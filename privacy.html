2. The short version

We built Shieldora to protect children, and collecting more than we need would work against that. So:

  • We do not keep a history of what your child looks at. We could not show you one if you asked, because we do not store it.
  • We never record the website, the page, the search or the message. Our filtering resolver has to look up an address to decide whether to allow it, but it does not write the address down. It is held in the resolver's memory only for as long as the answer stays valid, tied to no device, and never stored or logged.
  • When a site is blocked, all we record is which device, when, how many, and whether it was a family filter block or a security risk, so we can tell you a block happened. Never what the site was, unless you have turned on the optional detailed alerts described in 3.4, where that feature is available.
  • If you block an app or a type of site, we record your choice and count the blocks. Nothing about how the app was used.
  • We never sell your data, and we never share it for anyone's advertising or marketing.
  • We collect the least we can to run accounts, keep protection working, and tell you when something needs you.

This summary is for reading. The detail below is what governs.

3.3 From the child's device, for filtering

Filtering works in two layers, and both matter for what is and is not collected.

On the device. Apple's Family Controls apply a web-content filter in Safari and enforce the protections a parent has set (see 3.4). This runs on the phone. Apple reports individual blocks to nobody, including us.

Through our resolver. The child's phone is set to send its DNS lookups (the step that turns a web address into a network address) to a resolver we run, which forwards them to Cloudflare's 1.1.1.1 for Families for the filtering decision. This is how category filtering and forced safe search work. It means the child's DNS lookups pass through our resolver and Cloudflare's. The phone reaches our resolver through a small relay we run on Cloudflare's network (so that if our resolver is ever unreachable the lookup is still answered, by Cloudflare's family resolver directly, and the child is not cut off the internet). The relay passes the lookup on as it is, keeps nothing and logs nothing. What each does with them:

  • Our resolver does not store the address looked up. It reads the address to get an answer and keeps no log of it. Like any DNS resolver it holds recent answers in memory for the short time they stay valid (usually minutes, at most a few hours), so a second phone asking the same question gets a fast answer; that memory is shared across every device, is tied to none of them, and is never written to disk or a log. It does not store the child's IP address. The only thing it reports, and only when a lookup is blocked, is a one-way hashed form of the device's filtering token, the time, and the class of the block (see 3.4). Never the address, never the page, unless the optional detailed alerts in 3.4 are on for that child.
  • A blocked lookup is classed. When Cloudflare's family resolver blocks a name, our resolver asks Cloudflare's malware-only resolver (1.1.1.2) about the same name, once, after the block has already been answered, so the block can be described to you as a security risk (malware or phishing) or a family filter block (anything else Cloudflare's family filter blocks, which is mostly adult content; we are not told the reason). Only blocked names are asked about, never allowed ones; no client identifier is sent; the answer is remembered in the resolver's memory for the time Cloudflare says it is valid (at most six hours) so the same name is not asked about again.
  • Piracy streaming sites. If a parent turns on "Block piracy streaming sites" for a child, our resolver also blocks names on a public, community-maintained list of piracy and illegal streaming domains (HaGeZi's Anti-Piracy list, about 58,000 domains, licensed GPL-3.0, a copy of which ships with our resolver and is refreshed by us after review). The decision is made inside our resolver; Cloudflare is not asked about these names.
  • A short reviewed allow list. A small number of domains we have checked and found wrongly classed as adult by Cloudflare's family resolver (at the time of writing, one: a TikTok service domain) are sent to Cloudflare's malware-only resolver instead, so malware and phishing blocking still applies to them but the adult classification does not. The list ships with our resolver and is published in our source repository with the date and the reason for each entry; nothing is added without review.
  • Social app websites. If a parent blocks a social app for a child (see 3.4), our resolver also blocks that service's own website domains for that child's devices only. The decision is made inside our resolver from a short list we publish in the app (for example instagram.com for Instagram).
  • Shieldora's app makes periodic test lookups to confirm web filtering is working, and records only a time per device, never a website.
  • Our resolver keeps hourly totals of how many lookups it answered, served from cache, blocked, or failed, for 90 days. These are counts only, with no website, device or address.
  • Cloudflare receives the lookup in order to answer it. Cloudflare states that it deletes resolver logs within 25 hours, truncates IP addresses (it drops the last part of the address so it does not identify a single connection), and does not sell this data. We send Cloudflare no information about which client made a lookup (no EDNS Client Subnet), so a lookup reaching Cloudflare is not tied by us to a particular child.
  • The relay on Cloudflare's network sees what our resolver sees: the device's filtering token (the address the phone was given) and the lookup. It is code we wrote and control, running on Cloudflare's edge; it stores nothing, keeps no log (logging is switched off), and holds no state between lookups. When our resolver is unreachable it sends the lookup to Cloudflare's family resolver with no device identifier, so filtering continues but the block reporting in 3.4 pauses until our resolver is back.

Shieldora is not a VPN. Only DNS lookups go through our resolver; the child's web pages, messages and other traffic do not, and we never see them.

iCloud Private Relay. If iCloud Private Relay is on, Safari can send its lookups through Apple's relay instead of our resolver, which would go around the filter. So our resolver answers Apple's Private Relay setup lookups with "not available", which is Apple's own way for a network to switch Private Relay off. While Shieldora's web filtering is on, Private Relay does not run on the child's phone, and iOS may not show the child any notice about it. Once the phone is unlinked from Shieldora, Private Relay works as normal.

3.4 Protection records

We record whether protection is running and what a parent has set, not what a child does.

The settings a parent controls, and their current value:

  • The five device restrictions: app installation, account changes, passcode changes, automatic date and time, and explicit media.
  • The web-content filter (on or off).
  • Safe search, forced on by default for Google, Bing and DuckDuckGo, which a parent may turn off per child.
  • The browser list: which third-party browsers are blocked, and which a parent has allowed.
  • Social apps: which of Instagram, TikTok, Snapchat, Discord and Reddit a parent has blocked for a child (all allowed unless the parent blocks them). Blocking one blocks the app on the child's phone and its website through our resolver. We store only the parent's choice. We do not record whether, when or how long the app was used, and we are not told when the child tries to open a blocked app.
  • Social app schedules: if a parent sets times when a social app is blocked (for example a bedtime or school hours), we store the days and times the parent set and which app each one applies to. We do not record whether the child tried to open the app during a schedule.
  • Piracy streaming sites: whether a parent has turned on blocking of piracy streaming sites for a child (off unless turned on).
  • Detailed block alerts: whether a parent has turned on the optional detailed alerts described below (off unless turned on, and only where the feature is available).

The protection-status events we record:

  • A device's regular check-in, which is how we can tell protection is still running.
  • Protection going offline (check-ins stopping, whether the device is off, has no signal, or the permission was removed), and coming back.
  • Why a phone was quiet, where we can tell. When a phone checks in after a gap of an hour or more, and its start-up time shows it was switched off or restarted in the gap, or its last check-in before the gap showed a battery of 5% or less, we record one note saying so ("switched off from 9:15 pm to 7:05 am", or "probably ran out of battery"), shown in the app only; we do not send a notification or email for it. Where neither applies, nothing new is recorded.
  • A site was blocked. When the resolver blocks one or more lookups on a device, we record which device, the time of the first block, a count of how many distinct sites were blocked in a short burst (about 30 seconds), and how many of those were family filter blocks and how many a security risk. We never record the address or the search. The parent is told "a site was blocked on this device", never which site. Where three or more different sites are blocked within about ten seconds, the one record is marked as a likely burst of pop-ups or advertising, and the parent is told that this is usually caused by another website, not by the child visiting the sites directly.
  • A piracy streaming site was blocked, for a child whose parent turned that setting on: which device, the time of the first block, and a count. No address. The parent sees this in the app only; we do not send a notification or email for it, because the parent asked for the block.
  • A blocked social app's website was blocked, for a child whose parent blocked that app: which device, which app (for example "Instagram"), the time of the first block, and a count. No address. In the app only; no notification or email. We are not told, and do not record, attempts to open the blocked app itself.
  • Detailed block alerts, an optional feature that may not be available yet. Shieldora includes an optional setting, "more detail on block alerts", which may not be offered in your version of the app. Where it is offered and a parent switches it on for a child (which needs the parent's second factor), we also record the blocked site's domain (never the page, path or search) and whether it was a family filter block or a security risk. This is stored encrypted, shown only in the parent's app, never in a notification or email, deleted after 30 days, and deleted at once if the parent turns the setting off. The child's phone shows that it is on. It is off unless the parent turns it on, and while the feature is not offered nothing is recorded under it for anyone.
  • Web filtering may be off. If a child's phone keeps checking in but stops sending DNS through our resolver for about two hours, we note it and tell the parent that filtering may not be running (for example because a VPN or iCloud Private Relay is on, or the DNS setting was changed). This is a status, not an accusation, and the alert says so.
  • A parent allowing a third-party browser, or turning safe search off, which change what is filtered.
  • The alerts raised from any of the above, and whether each was delivered.

How a block reaches your dashboard. The child's phone carries a secret filtering token. Our resolver only ever sees and handles a one-way hash of that token (a fingerprint it cannot be turned back into), and reports a block to our server as that hash, a time and a class. The server matches the hash to the right device on your account and stores the block against that device. The token itself is never written to a log. This is so a resolver record cannot be replayed as a working credential, and so the record is the minimum that still lets us attribute a block to the right child on the parent's dashboard.

4. What we deliberately do not collect

Written to be held to.

  • No browsing history. We do not build, store or have any way to read a record of the sites a child visits. Where the optional detailed block alerts are offered and turned on by the parent for a child, we keep the domains of blocked sites for 30 days (see 3.4). We still never record the sites a child visits that are not blocked.
  • No web addresses stored, unless a parent turns on detailed alerts. Our resolver looks up an address to filter it and does not write it down; Apple's on-device filter reports nothing to us. By default, no address a child visited is stored by Shieldora. With detailed alerts on, the domain of a blocked site is stored, encrypted, for 30 days.
  • No app usage. When a parent blocks a social app we record the parent's choice and count blocked attempts to reach the app's website. We do not record which apps a child uses, for how long, or when.
  • No page content. We never see or store what was on a page.
  • No message content. We do not read or collect messages, emails or chats in any app.
  • No search terms. We do not record or detect what a child searches for. Forced safe search changes the result a search engine returns; it does not report the search to us.
  • No location data.
  • No contacts, photos, camera or microphone.
  • No advertising identifiers, and no tracking across other apps or sites.

A limit we want to be honest about

Filtering covers web content, mainly in Safari. Other browsers are blocked by default; if a parent allows one, content inside that browser is not filtered, and the app says so when they allow it. Content inside other apps (for example YouTube) is served by those apps and is not reached by web filtering; we do not see it and cannot block it. A parent can block five named social apps outright (3.4), which blocks the app by its identifier and its website; an app that is not on that list is not blocked, and a child who is allowed to install apps may install one that is not listed. The piracy list and the social app domain lists are maintained by people, and a list can be wrong about a site; the app describes such a block as "Streaming site blocked (piracy list)" so it is clear the description comes from the list, and the setting says the list will not catch every piracy site. In the same way, a block from Cloudflare's family filter is shown as "Family filter", not "Adult", because we are not told why Cloudflare blocked it and its filter can be wrong (for example, it has classed some anime streaming sites as adult). No filter catches everything. What Shieldora offers is not a promise that nothing is ever seen, and not a report of what was blocked, but filtering plus a clear signal to the parent when protection stops running.

5. Children's data

Shieldora is used by children, on children's devices, at a parent's direction, and stricter rules apply.

The parent holds the account. Children do not have their own accounts, do not sign in, and cannot sign out. A child device holds only a limited credential that lets it report status and receive settings. A child cannot read the parent dashboard or change anything.

We collect, about a child: a display name or nickname the parent chooses. We encourage a nickname over a real name. We do not ask for or store a child's age or date of birth.

6. Parental consent, and how we use data

The parent sets up the account, links each child's device, and must approve every change that reduces protection with a fresh two-factor code (turning protection off, allowing a browser, turning safe search off, unlinking a device, deleting or shortening a social app schedule, deleting the account). Changes that increase protection need no code, so a parent who cannot reach their authenticator can always restore it. Each time a parent consents we record when, how, and which version of this notice they were shown.

We use the information above only to: run accounts and sign parents in; verify protection changes with two-factor; apply and update filtering on a child's device; detect that protection has stopped and alert the parent; send those alerts by push notification and email; manage the subscription; provide support; keep the service secure and investigate abuse; and meet our legal obligations.

We do not use any of it for advertising, marketing profiles, or training machine-learning models.

9. How we protect it

  • Encrypted in transit, and encrypted at rest by our providers.
  • Passwords stored only as cryptographic hashes.
  • Two-factor on parent accounts, required for every protection-reducing change and for account deletion.
  • Child devices hold only a limited credential, and the filtering token is stored by our resolver only as a one-way hash. On our server the filtering token is stored encrypted, and opened only to tell the child's own phone its filtering address.
  • Access to production data is restricted to one person, the founder, who operates the service, and is logged. Shieldora is run by one person, and we would rather say so than imply a team and an approval process that do not exist.

No service can promise perfect security, and we do not.
